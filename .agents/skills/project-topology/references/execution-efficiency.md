# Evidence-based execution efficiency

Use when compiling or amending a substantial plan that includes repairs, fragile
controls, repeated external commands, or recovery. Apply the relevant obligations
inside existing policies, module actions and cards; do not add a universal gate,
telemetry ledger, runtime service, or extra plan artifact. This reference governs
planning and dispatch contracts, not permission to execute the planned work.

## Rehearse changed controls through their real decision boundary

For a changed fragile runner/control, map each changed branch to an executable
test using realistic typed objects or disposable fixtures. Reach its decision,
result and cleanup boundary. Source-string/order checks can supplement this but
cannot establish executable readiness. Identify the producer of every awaited
event and prove the producer can run before the consumer blocks. Cover parser
rejection before structured output, post-retirement state, and cleanup claims
where relevant; zero attempted cleanup operations cannot prove a known-live
process absent. Check exact identity/state, not a success label alone.

Rehearse checkpoint continuation with completed and preserved units, not only a
cold manifest. Supply the complete fixture dependency closure, including unchanged
helpers. Bind executable configuration semantically rather than searching comments
for an expected value. Reuse unaffected readiness credit. Select a representative
live canary only for a property that cannot be established locally and only within
existing authority; do not add one by default. Apply the shared
[acceptance-design decisions](acceptance-design.md): justify both this environment
and the number/variation of observations needed. "Representative" does not waive
distinct required claims; structural matrix completeness does not justify additional
external work. The shared decisions apply at every tier and do not mandate this
particular readiness/canary pattern where its triggering risks are absent.

## Compare the requirement with the assertion before product repair

M05 must compare the exact requirement clause, observed behavior and failing
assertion before assigning a mutation goal. If the assertion demands an uncertain
platform guarantee, first assign a focused contract/feasibility inquiry with open
findings. Its answer may be product defect, oracle exceeds contract, or unresolved.
Do not pre-decide that research must produce a product patch, or automatically
weaken a valid requirement to make a test pass.

Carry adjudicated mechanism groups into runtime repair cards. Merge groups only
when one shared invariant, source context and proof make a combined writer useful;
the same role name is insufficient. Serialize overlapping writes. Batch compatible
findings rather than creating one lane per file or failure. Each card consumes
retained findings, answered questions, accepted credit and the first unresolved
executable action. An already narrow card that ignores that action needs observed
supervision, not further copies of the same instructions.

## Make fixed command queues explicit

For an approved fixed command list, name its executor, checkpoint store,
terminal-result handler and aggregate publisher. Prefer an existing deterministic
runner, or a small justified implementation, for mechanical advancement. Maintain
**one outstanding wait per process handle**. On terminal exit or an unknown-handle
error, reconcile the durable unit checkpoint, output and exact process identity;
do not blindly poll, relaunch or replay a side effect. Ordinary failures continue
the remaining preauthorized independent commands. Changed scope, target, scenario
or attempt returns to the owning authority.

M08 rehearses ordinary failure, terminal exit, lost handles and interrupted resume,
including preservation of completed units and single aggregate publication.
If runtime automation is absent, label supervision MANUAL/ORCHESTRATOR_POLICY and
give a named owner the same rules; do not call prose RUNTIME_ENFORCED. A new service
is not mandatory, but automatic advancement cannot be promised without code proof.

## Observe progress and finish completed work

P02 names who observes progress, the task-specific evidence signal, its delivery
surface, the observation point, and the action on repeated unchanged failure.
Distinguish RUNNING, WAITING_FOR_COMMAND, READY_TO_REPORT and BLOCKED. A new
experiment or eliminated hypothesis may be progress without an edit. Elapsed time,
silence and item counts alone are not nonprogress. Do not impose a universal
five-minute agent deadline or change the two same-thread result-correction attempts
specified by worker-continuity-and-recovery.md.

Carry answered questions and the first incomplete action through compaction and
replacement. When discovery is complete, use the existing mechanical validator or
aggregator and publish the terminal packet; do not reopen accepted investigation.
Contain only exact owned identities on an evidenced trigger. A replacement must
change a failed prerequisite, task boundary or next action, not repeat a monolith.

## Diagnose the actual launch context and emit results mechanically

Read native terminal errors before modifying wrappers or retrying unchanged
launches. Bind admission to the exact credential/configuration home consumed by
the launch and its relevant freshness conditions. Another home's past auth success
is not current admission. Use only necessary authorized probes and never expose
credential contents. Authentication success does not prove tool permissions.
Preserve user-owned model selection, primary retries and fallback conditions.

Instantiate the native result-emitter command with actual context, facts, output
and handoff paths before dispatch; no placeholder ellipses. Reuse the native
serialization/schema/digest tools and read back their output. Keep report-only
correction in the existing administrative route and preserve product credit unless
its consumed semantics changed. Do not synthesize findings, rewrite intentional
malformed-result test inputs, or normalize a substantive failure into PASS.
Compatible corrections may share one review/integration packet; substantive repairs
retain required independent review and integration. Do not replay unchanged smoke
solely because an administrative boundary was crossed.

## Compare schedules without inventing savings

For proposed serial edges, name the dependency, shared mutable resource, authority
constraint or unresolved isolation fact. Compare a safe concurrent alternative
where plausible, accounting for nested process fanout, credential refresh, caches,
cleanup ownership and provider quotas. Separate worktrees or spare agent slots do
not prove external capacity. Record the smallest qualification needed to change
the schedule and keep existing limits until it passes and the graph/capacity change
is authorized. Prefer examining separate provider groups before same-provider use.

Separate observed durations, overlapping lane effort and estimated critical-path
savings. A failed lane's whole duration is not automatically removable. Measure
from existing evidence when available; leave unknown savings unknown. Do not turn
an incident count or hypothetical two-worker schedule into a promised speedup.

## Semantic acceptance examples

Before accepting the amendment, trace these applicable cases against its text:
an absent typed field fails locally; a circular wait cannot pass readiness; an
overstrong oracle gets a contract decision before mutation; unrelated repair groups
stay separate; an unknown handle cannot trigger blind replay; completed analysis
goes to publication after compaction; a stale credential copy triggers native-error
diagnosis; a BOM/digest correction preserves substantive credit; and unqualified
shared credentials do not acquire parallel workers. Mark missing runtime proof as
pending rather than claiming these examples were executed by the structural parser.
